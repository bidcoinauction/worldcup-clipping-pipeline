# Operating Model

## Terminology

Avoid starting with workspace-first language. The broader business model should be:

```text
Organization
  -> Projects
    -> Workflows
      -> Jobs
        -> Outputs
          -> Assets
```

This hierarchy works for a sports league, creator, conference organizer, podcast network, or media company.

## Organization

An organization is the paying customer or managed account.

Examples:

- Regional basketball league.
- Football club.
- Twitch creator business.
- Conference organizer.
- Podcast network.

Organization data should eventually include:

- Legal name.
- Public brand name.
- Contacts.
- Billing owner.
- Approval owner.
- Rights owner.
- Default brand system.
- Default delivery destinations.

Current repo support:

- Missing.

## Project

A project is a scoped body of work inside an organization.

Examples:

- 2026 season.
- Weekly podcast production.
- Annual conference.
- Tournament weekend.
- Archive processing sprint.

Project data should eventually include:

- Project name.
- Date range.
- Content goals.
- Source rules.
- Approval rules.
- Delivery rules.
- Reporting requirements.

Current repo support:

- World Cup schedule and match manifests partially act like a project, but are hardcoded to one tournament.

## Workflow

A workflow is a repeatable business process applied to a project.

Examples:

- Game highlights.
- Short-form social production.
- Podcast quote extraction.
- Conference speaker highlights.
- Localization.
- Archive indexing.

Workflow data should eventually include:

- Source adapter.
- Transcription provider.
- Analysis template.
- Export profile.
- Review workflow.
- Delivery destination.

Current repo support:

- Scripts represent workflows implicitly. There is no first-class workflow model.

## Job

A job is one execution of a workflow against one source or batch.

Examples:

- Process game 17.
- Process episode 42.
- Process keynote session.
- Process livestream VOD from Friday.

Job data should eventually include:

- Job ID.
- Status.
- Source assets.
- Started and completed timestamps.
- Logs.
- Costs.
- Errors.
- Outputs.

## Output

An output is something generated by a job for review, delivery, publishing, or archive use.

Examples:

- Exported clip.
- Transcript.
- Captions.
- Thumbnail prompt.
- Social copy.
- Metadata package.
- Review dashboard.

Output data should eventually include:

- Output type.
- Status.
- Review result.
- Delivery status.
- Associated assets.
- Created by job.
- Version.

Current repo support:

- Outputs exist as files and manifests, but there is no generic output model.

Current repo support:

- Match manifests and live registry files partially track job state, but there is no durable generic job system.

## Asset

An asset is a source or supporting file used by workflows or attached to outputs.

Examples:

- Original media.
- Logos.
- Fonts.
- Templates.
- Brand kits.
- Reference files.
- Source transcripts.
- Intermediate files.

Asset data should eventually include:

- Asset type.
- File path or URI.
- Provenance.
- Rights status.
- Created by job.
- Review status.
- Delivery status.

Current repo support:

- Assets exist as files, but metadata is spread across CSV, JSON, and folders.

## Early Agency Version

Before building software models, use this hierarchy operationally:

- One folder per organization.
- One project plan per engagement.
- One workflow template selected manually.
- One job log per source file.
- One manifest listing all outputs and assets.
